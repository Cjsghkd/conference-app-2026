# Enforcement checker tests

Every FIR checker in `:tools:compiler-plugin` (see [Enforcement](./enforcement.md)) has a diagnostic
test built on JetBrains' own compiler test framework, published as
`org.jetbrains.kotlin:kotlin-compiler-internal-test-framework`. A test compiles a Kotlin source file
with the plugin loaded and asserts that the diagnostics land on exactly the marked source ranges.

```bash
./gradlew :tools:compiler-plugin:test
```

## Layout

| Directory | Contents |
| --- | --- |
| `testData/diagnostics/` | One source file per rule, carrying the expected diagnostics as markers |
| `test-fixtures/` | The abstract test runner and the configurator that loads the plugin |
| `test-stubs/` | Stand-ins for the app and library types the test sources resolve against |
| `test-gen/` | JUnit 5 classes generated from `testData/`; regenerated by the build, not committed |

## Test data

A `<!DIAGNOSTIC_NAME!>…<!>` pair marks the exact range the diagnostic is expected on. Unmarked code
must produce no diagnostic, so each file states both the rejected and the accepted shape:

```kotlin
class Counter {
    private var mutableCount = 0
    val <!PROPERTY_MUST_USE_PRIVATE_SET!>count<!>: Int get() = mutableCount
}

class CounterWithPrivateSet {
    var count: Int = 0
        private set
}
```

`// FILE: Name.kt` splits one test data file into several compiled files. Use it when a rule reads
the file name, or to keep a rule that matches on declaration names from tripping another rule.

Checkers match types by fully qualified name, so test data resolves its imports against `test-stubs/`
rather than the real modules — a stub declares only the shape a checker reads. A rule that keys on a
new type needs the matching stub added there.

The Compose compiler plugin's FIR extension is registered alongside the enforcement plugin, so
`@Composable` function types in test data carry the same function-type kind they do in the app build.

## Adding a rule's test data

1. Write `testData/diagnostics/<ruleName>.kt` with the rejected and accepted shapes, without markers.
2. Fill in the expected markers:

   ```bash
   ./gradlew :tools:compiler-plugin:test -Penforcement.updateTestData=true
   ```

   Each test data file is rewritten with the diagnostics the plugin actually reported. Read the diff:
   it is a record of current behaviour, not of intended behaviour.
3. Run the suite without the flag to confirm it passes.

## Compiler artifacts

The test framework runs against the un-shaded `kotlin-compiler`, so `:tools:compiler-plugin` compiles
against that artifact. The Kotlin Gradle plugin instead loads compiler plugins into
`kotlin-compiler-embeddable`, whose IntelliJ classes live under `org.jetbrains.kotlin.com.intellij`.
Every module therefore consumes the relocated jar produced by `shadowJar`, never the plain one.

## Coverage

Diagnostics are reported on FIR source elements, which the framework gives the path `/<file name>`.
`PlatformOnlyNaming`'s reverse direction — a platform prefix requires `@PlatformOnly` — is gated on a
`/commonMain/` path segment and so is covered only by the app build, not by this suite.
